# B2: Debug arquitetural

## a) Saída do pipeline original (CLASSE_ALVO = "Granel")
Executado exatamente como no enunciado (mongo/B2a.out.txt):

[ { _id: { terminal: 'T1', classe: 'Granel' }, kg_total: 0, mov: 20226 } ]

Plano: GROUP > COLLSCAN, totalKeysExamined 0, totalDocsExamined 400.000, 20 grupos
criados no $group, 3 após o $limit, 1 após o $match final. Resultado errado: o
kg_total é 0 e só 1 terminal aparece, em vez dos 3 de maior peso.

## b) Defeitos encontrados

| # | Defeito | Tipo | Mecanismo |
|---|---|---|---|
| 1 | `$sum: "peso_kg"` sem `$` | Lógica | Sem `$`, "peso_kg" é uma string literal, não um caminho de campo. O $sum ignora valores não numéricos, então kg_total = 0 em todos os grupos (confirmado na saída). |
| 2 | `$project: { terminal: 1, classe: 1 }` no início | Lógica | O $project descarta peso_kg antes do $group. Mesmo corrigindo o `$`, a soma continuaria 0, porque o campo já não existe no documento. |
| 3 | `$limit: 3` antes do `$sort` | Lógica | O limit corta 3 grupos arbitrários (ordem do hash do $group) antes de ordenar. Os 3 maiores podem ficar de fora. |
| 4 | `$match` por classe no final | Lógica | O filtro roda depois do limit, sobre 3 grupos arbitrários: ao filtrar sobram 0 a 3 resultados (aqui, 1) e não os 3 maiores da CLASSE_ALVO. |
| 5 | `$match` no último estágio | Desempenho | Como não há filtro no início, o plano é COLLSCAN: 400.000 documentos lidos, mesmo havendo o índice {classe, ts, terminal, peso_kg}. O filtro no 1º estágio habilitaria IXSCAN. |
| 6 | Agrupar por { terminal, classe } sobre todas as classes | Desempenho | Cria 20 grupos e processa 4x mais documentos do que o necessário, sendo que só a CLASSE_ALVO interessa. Filtrando antes, o _id vira só o terminal (5 grupos). |
