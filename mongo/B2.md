# B2: Debug arquitetural

## a) Saída do pipeline original (CLASSE_ALVO = "Granel")
Executado exatamente como no enunciado (mongo/B2a.out.txt):

[ { _id: { terminal: 'T1', classe: 'Granel' }, kg_total: 0, mov: 20226 } ]

Plano: GROUP > COLLSCAN, totalKeysExamined 0, totalDocsExamined 400.000, 20 grupos
criados no $group, 3 após o $limit, 1 após o $match final. Resultado errado: o
kg_total é 0 e só 1 terminal aparece, em vez dos 3 de maior peso.

## b) Defeitos encontrados

| # | Defeito | Tipo | Mecanismo |
|---|---|---|---|
| 1 | `$sum: "peso_kg"` sem `$` | Lógica | Sem `$`, "peso_kg" é uma string literal, não um caminho de campo. O $sum ignora valores não numéricos, então kg_total = 0 em todos os grupos (confirmado na saída). |
| 2 | `$project: { terminal: 1, classe: 1 }` no início | Lógica | O $project descarta peso_kg antes do $group. Mesmo corrigindo o `$`, a soma continuaria 0, porque o campo já não existe no documento. |
| 3 | `$limit: 3` antes do `$sort` | Lógica | O limit corta 3 grupos arbitrários (ordem do hash do $group) antes de ordenar. Os 3 maiores podem ficar de fora. |
| 4 | `$match` por classe no final | Lógica | O filtro roda depois do limit, sobre 3 grupos arbitrários: ao filtrar sobram 0 a 3 resultados (aqui, 1) e não os 3 maiores da CLASSE_ALVO. |
| 5 | `$match` no último estágio | Desempenho | Como não há filtro no início, o plano é COLLSCAN: 400.000 documentos lidos, mesmo havendo o índice {classe, ts, terminal, peso_kg}. O filtro no 1º estágio habilitaria IXSCAN. |
| 6 | Agrupar por { terminal, classe } sobre todas as classes | Desempenho | Cria 20 grupos e processa 4x mais documentos do que o necessário, sendo que só a CLASSE_ALVO interessa. Filtrando antes, o _id vira só o terminal (5 grupos). |

## c) Pipeline corrigido

db.movimentacoes.aggregate([
  { $match: { classe: "Granel" } },
  { $group: { _id: "$terminal", kg_total: { $sum: "$peso_kg" }, mov: { $sum: 1 } } },
  { $sort: { kg_total: -1 } },
  { $limit: 3 },
  { $project: { _id: 0, terminal: "$_id", kg_total: 1, mov: 1 } }
])

Saída (mongo/B2b.out.txt):

| terminal | kg_total | mov |
|---|---|---|
| T1 | 324.176.962 | 20.226 |
| T5 | 323.933.209 | 20.111 |
| T2 | 320.843.638 | 20.029 |

**Comprovação independente:** somei o peso de cada terminal em consultas separadas
(`$match` por classe e terminal + `$group`), obtendo T1 = 324.176.962, T2 = 320.843.638,
T3 = 317.625.006, T4 = 318.786.449 e T5 = 323.933.209. Os 3 maiores (T1, T5, T2),
os totais e as contagens coincidem exatamente com a saída do pipeline corrigido.

**Plano (explain):** GROUP > PROJECTION_COVERED > IXSCAN, índice
classe_1_ts_1_terminal_1_peso_kg_1 com bounds classe = "Granel".
totalKeysExamined 100.340, totalDocsExamined 0, 5 grupos, 3 retornados.

## Comparação original x corrigido

| | Original | Corrigido |
|---|---|---|
| Stage de entrada | COLLSCAN | IXSCAN (coberto) |
| Documentos lidos | 400.000 | 0 (100.340 chaves do índice) |
| Linhas entrando no $group | 400.000 | 100.340 |
| Grupos criados | 20 | 5 |
| Resultado | 1 doc, kg_total = 0 (errado) | 3 docs, totais corretos |
| executionTimeMillis | 142 | 46 |

## d) Impacto da refatoração
Ao mover o `$match` para o primeiro estágio, o pipeline passou a usar o índice
{classe, ts, terminal, peso_kg}: em vez de um COLLSCAN sobre 400.000 documentos, é um
IXSCAN coberto (totalDocsExamined 0), que só lê as chaves da classe Granel (100.340,
cerca de um quarto). Na CPU, caiu a 1/4 o volume de linhas que passam pelo $group,
e o $sort sobre 5 grupos com $limit 3 é trivial; o ganho de tempo observado
(142 ms para 46 ms) depende do hardware e não é o critério, o que conta é a redução do
trabalho. Em RAM, o estado do $group caiu de 20 para 5 grupos (peakTrackedMemBytes
2.700 para 550 bytes), um ganho pequeno em absoluto, porque as acumulações são
leves. O ganho relevante de memória é indireto: o COLLSCAN carrega no cache do
WiredTiger os documentos inteiros da coleção (poluindo-o), enquanto o IXSCAN coberto
só traz páginas de índice. O resultado também passou a estar correto, pois o
`$sum: "$peso_kg"` agora enxerga o campo e o `$sort` precede o `$limit`.
